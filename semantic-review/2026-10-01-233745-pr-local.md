# CoC 7e tabletop — acceptance review of sheet, dice, combat, and whiteboard

The two committed feature drops build out the full virtual tabletop: character sheet with derived stats, a CoC 7e rules engine, a combat grid with token/initiative handling, and a collaborative whiteboard. This review checks the five acceptance criteria the user called out and sweeps for the runtime bugs they flagged. The headline: all five criteria hold in the code as written, with one genuine correctness caveat on the dice fumble rule under a specific target range, plus several real runtime hazards (division-by-zero producing `NaN` bar widths, and a broadcast/localStorage write on every pointer move).

Watch for:
- **Division by zero → `NaN` geometry** when a resource `max` is 0 (`maxMP` is 0 for POW<5, `maxHP` can be 0 for low CON+SIZ). Breaks both the sheet bar and the combat token bars. *(confirmed)*
- **Fumble rule is correct per the stated spec but diverges from published CoC 7e** at target ≥ 50 (96–99 should still be a fumble only when roll > target; here 96–99 is a plain fail, which matches the user's spec). Flagged as a spec-vs-canon note, not a bug against the given criteria. *(confirmed)*
- **Every pointer-move during a token drag (combat) or element drag (whiteboard) triggers a `localStorage` write + cross-tab broadcast.** Functional but a write storm. *(confirmed)*

**Verdict**: APPROVED

## High-level view

The HP/MP independence requirement holds structurally: each resource pool is a self-contained `{current, max}` object, every edit path patches exactly one field, and the only cross-field recompute is characteristic-driven (POW recalculates SAN and MP, CON/SIZ recalculate HP) — MP edits never reach into HP. The dice classifier implements the stated fumble/critical/extreme/hard/regular ladder faithfully; the one thing to be aware of is that the "96–99 only when target<50" rule is the user's spec and the code matches it, which is a deliberate simplification of the canonical rule. Ammo gating is enforced consistently at both the sheet buttons (disabled + blocked in the handler) and the combat `doAttack` path, with consumption on fire. The whiteboard background only spawns a note when the note tool is active, arrows dedupe bidirectionally and attach to any element type, and editing a note's text in select mode stops drag from starting. Combat requires a selected target before an attack resolves (guarded in the handler and the button `disabled`), and HP changes route through the linked character so the sheet and token bar stay in sync. The remaining concerns are runtime robustness: `NaN` widths when a `max` is zero, and persistence being driven on every pointer move.

<details>
<summary>Issues (6)</summary>

1. **Resource-bar division by zero** — `ResourcePips` computes `(current/max)*100` with no guard; when `max` is 0 (MP at POW<5, or HP at very low CON+SIZ) the width becomes `NaN%`. Guard with `max > 0 ? ... : 0`.
2. **Combat token-bar division by zero** — token HP/SAN bars compute `(current/max)*r*2` with the same unguarded division; a token mirroring a zero-max pool renders `NaN` width. Same guard needed.
3. **Fumble rule vs. canonical CoC 7e** — `classifyRoll` treats 96–99 as fumble only when `target < 50`, matching the user's stated spec but not the published rule (96–99 is a fumble whenever it is also a failure). Confirm the simplified rule is intended.
4. **Persistence write-storm on drag** — both `combat.patchToken` (combat drag) and `commit` (whiteboard drag) run `sync.save` + `sync.broadcast` on every `pointermove`. Throttle or defer persistence to pointer-up.
5. **Whiteboard note not draggable by its body** — in select mode the textarea stops propagation so the note can only be moved by its border/non-text chrome; intended for editing but worth confirming the drag affordance is discoverable.
6. **Combat uses only `weapons[0]`** — `doAttack` always picks the attacker's first weapon regardless of ammo state on other weapons; a character whose first weapon is a depleted firearm is blocked even if they have a melee weapon. Confirm single-weapon assumption.

### HP and MP are structurally independent pools

Each resource is a `ResourcePool` (`{current, max}`) stored as a separate field on `Character` (`hp`, `san`, `mp`, and `luck` as a bare number). The sheet wires each `ResourcePips` to patch only its own slice — `onChange={(hp) => patch({ hp })}`, `onChange={(mp) => patch({ mp })}` (`src/pages/SheetPage.tsx:268-277`). `ResourcePips.set` reconstructs only the pool it was handed (`onChange({ ...pool, current: clamp(current) })`, `src/components/sheet/ResourcePips.tsx:22`), so a PM pip or ± button can only ever write back into `mp`. There is no shared mutable state between pools.

The single place where one field recomputes another is characteristic-driven: in `applyCharacteristic`, a POW change recalculates SAN and MP maxima, and a CON/SIZ change recalculates HP (`src/pages/SheetPage.tsx:77-91`). Critically, the POW branch touches `san` and `mp` but never `hp`, and the CON/SIZ branch touches only `hp`. So the criterion holds: no code path lets an MP mutation alter HP. *(confirmed)*

### Dice fumble rule matches the spec but diverges from canon

`classifyRoll` (`src/domain/cocRules.ts:93-104`) orders the ladder as the criterion requires — critical (`roll === 1`) first, then fumble, then floor-based extreme/hard/regular/fail — so 01 wins over the extreme threshold.

The caveat is the fumble line `roll === 100 || (target < 50 && roll >= 96)` (`src/domain/cocRules.ts:96`). It matches the user's stated rule exactly, but diverges from published CoC 7e, where 96–99 is a fumble whenever the roll also fails (for any target); here, at target ≥ 50 a 96–99 is a plain fail. The code matches the acceptance criterion — flagged only so the simplification is a conscious choice. *(confirmed)*

### Ammo gating is enforced on both attack paths

The requirement is enforced on both paths. On the sheet, `WeaponTable` disables all three hit buttons when `noAmmo = w.ammoCapacity != null && (w.ammoCurrent ?? 0) <= 0` (`src/components/sheet/WeaponTable.tsx:40,56-58`), and the `attack` handler hard-blocks and decrements (`if ((w.ammoCurrent ?? 0) <= 0) return;`, `src/pages/SheetPage.tsx:121-125`). In combat, `doAttack` repeats the guard and consumes a round on fire, alerting and returning before any roll (`src/pages/CombatPage.tsx:150-155`). Melee weapons (`ammoCapacity == null`) skip the check.

One scoping note: `doAttack` always resolves `weapon = c?.weapons[0]` (`src/pages/CombatPage.tsx:146`). A character whose first weapon is a depleted firearm is blocked from attacking in combat even if they carry a usable melee weapon. If multi-weapon selection in combat is out of scope this is fine, but the single-weapon assumption is worth confirming. *(confirmed, severity low)*

### Whiteboard: background note creation, arrow dedupe, and edit-vs-drag

Background clicks only create a note when the note tool is active — `onBackgroundPointerDown` gates note creation behind `if (tool === "note")` and otherwise falls through to draw or pan/select (`src/pages/WhiteboardPage.tsx:97-120`). Select/pan on the background only starts a pan and clears selection. So the "no accidental notes" criterion holds. *(confirmed)*

Arrows attach to any element via `onElementPointerDown` under the arrow tool, which is type-agnostic (notes, images, PDFs all route through the same handler, `src/pages/WhiteboardPage.tsx:181-186`). Duplication is prevented by a bidirectional existence check before pushing — `exists` tests both `from→to` and `to→from` (`src/pages/WhiteboardPage.tsx:189-195`), and self-arrows are blocked by `arrowFrom !== el.id`. So arrows don't duplicate and work on every element type. *(confirmed)*

Dragging a note while editing its text is handled: the textarea is `disabled` unless `tool === "select"`, and in select mode its `onPointerDown` stops propagation so the drag-start on the parent element never fires while you're clicking into the text (`src/pages/WhiteboardPage.tsx:390-394`). The consequence is that the note can only be *moved* by grabbing non-textarea chrome (the border/inner padding), since a pointer-down on the text area is swallowed. That is the correct trade-off for "don't drag while editing," but the drag affordance is subtle — worth confirming it's discoverable. *(confirmed)*

### Combat requires a target and propagates HP to the linked sheet

Target gating is enforced in both the handler (`if (!target) { alert(...); return; }`, `src/pages/CombatPage.tsx:143`) and the button (`disabled={!target}`). Target selection is a separate per-token "◎" toggle on `targetId`, distinct from selection. *(confirmed)*

HP propagation: for linked tokens, `applyDamageToToken` clamps against `characters[cid].hp` and calls `patchCharacter(cid, { hp, dying })` (`src/pages/CombatPage.tsx:131-139`); because token bars read HP via `tokenHP(t) = t.characterId ? characters[t.characterId]?.hp : t.hp` (`src/pages/CombatPage.tsx:56`), the single store write updates both the token bar and the sheet. Freestanding tokens fall back to `t.hp`. *(confirmed)*

### Division by zero yields `NaN` bar geometry

`maxMP` is `floor(POW/5)` (0 for POW < 5) and `maxHP` is `floor((CON+SIZ)/10)` (0 for CON+SIZ < 10), so a zero-max pool is reachable. `ResourcePips` renders its bar branch as `width: ${(pool.current / pool.max) * 100}%` with no zero guard (`src/components/sheet/ResourcePips.tsx:55`); the pips branch is safe since it iterates `Array.from({length: max})`, but the bar expression still divides by zero when it renders a zero-max pool.

The live hazard is the combat token bars: `width={Math.max(0, (hp.current / hp.max) * r * 2)}` and the SAN equivalent. `Math.max(0, NaN)` is `NaN`, so a token mirroring a zero-max pool renders a `NaN` width attribute. Guard both with `max > 0 ? current/max : 0`. *(confirmed)*

### Persistence fires on every pointer move during a drag

Both drag paths persist synchronously per move. In combat, `onMove` calls `combat.patchToken(id, {cx, cy})` on each `pointermove` (`src/pages/CombatPage.tsx:95-98`), and `patchToken` → `commit` → `persist` writes `localStorage` and broadcasts to other tabs every time. The whiteboard is the same shape: `onPointerMove` calls `commit({...})` for drag/resize on every move (`src/pages/WhiteboardPage.tsx:129-146`), and `commit` runs `sync.save` + `sync.broadcast`. For a smooth drag this is dozens of writes/broadcasts per second. It works, but it is a write storm that will show up as jank and cross-tab thrash; deferring persistence to pointer-up (keeping only local state updates mid-drag) is the usual fix. *(confirmed)*

### Pointer-handler closures are not stale

The user asked specifically about stale closures in the pointer handlers. The handlers (`onMove`, `onPointerMove`, `onElementPointerDown`, `commit`) are plain functions re-created on every render and attached inline, so each render's handler closes over that render's `board`/`view`/`drawing` state — there is no `useCallback`/`useEffect` capturing a stale value. `toWorld` is memoized on `[view]` and recomputed when the view changes. So the pointer flow does not suffer the classic stale-closure bug; no action needed here. *(confirmed — no issue)*
